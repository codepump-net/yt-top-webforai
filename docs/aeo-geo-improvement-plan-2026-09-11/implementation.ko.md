# 개발·검토·자동 배포 실행안

이 문서의 필드·파일 추가는 **후속 구현 제안**이다. 현재 앱에 존재하는 기능과 추가할 기능을 구분한다. 기술 기반은 현재 Next.js 정적 내보내기·React·TypeScript·GitHub Actions·GitHub Pages를 유지한다. 이번 개선의 중심은 질문 답변과 사실·근거 관리이며 프레임워크 교체가 아니다.

## 3. 공통 사실과 구조화 데이터

주소는 시·구·도로명·층 등의 구조화 필드에서 사람이 읽는 주소와 `PostalAddress`를 함께 만든다. 전화는 동일 원장에서 화면·전화 링크·메타 설명·JSON-LD로 전달한다. 현재 홈 소개의 전화번호, 방문 소개의 시간, `site.ts`의 별도 주소 문자열을 대상으로 제거·참조화한다.

본문에서 공통 사실이 필요하면 허용된 사실 ID를 참조하고 빌드에서 해석한다. 허용하지 않은 토큰이나 미확정값을 완성된 문장으로 렌더링하지 않는다. 사실 참조가 포함된 meta description도 같은 해석기를 거쳐 길이·고유성·최종 텍스트를 검사한다. 한 사실을 바꿨을 때 기존 숫자가 본문·메타·직렬화 텍스트에 남는지도 확인한다.

진료시간 모델에는 요일별 구간과 휴게 적용을 두고 검사별 접수 마감은 별도 정보로 둔다. 점심에 실제 진료하지 않는다고 확인된 구간은 나누어 표현한다. 토요일·휴일을 평일 규칙에서 추정하지 않는다. 날짜별 예외를 확인·유지할 수 있을 때만 해당 날짜 데이터를 사용하고 원래 공지 채널과 대조한다. 위치·시간을 구조화할 수 있지만 사실 확인과 화면 일치가 우선이다. [Google LocalBusiness 안내](https://developers.google.com/search/docs/appearance/structured-data/local-business), [구조화 데이터 품질 기준](https://developers.google.com/search/docs/appearance/structured-data/sd-policies).

확인된 지도 URL은 `hasMap`, 확인된 좌표는 `geo`, 확인된 시간은 `openingHoursSpecification`으로 생성한다. 해당 값이 없다고 임의의 기본 좌표나 24시간 영업을 넣지 않는다. 병원 ID `https://yttop.co.kr/#clinic`은 계속 공유한다. 새 사이트의 페이지·의료진 프로필 ID는 새 주소 안에서 안정적으로 유지한다. 다른 병원의 저자 ID와 경력을 복사하지 않는다.

## 4. 주장별 근거와 실제 의료진 연결

후속 데이터 계약에서 다음 개념을 분리한다. 아래는 필드 설계안이며 실제 근거·검토 완료를 뜻하지 않는다.

| 개념 | 제안 필드 | 검증 |
|---|---|---|
| 출처 | `id`, `url`, `title`, `publisher`, `sourceType`, `checkedAt`, `publishedOrUpdatedAt` | 열람일과 원문 갱신일 구분; 없으면 null |
| 의학 주장 | `id`, `pageId`, `blockOrQuestionId`, `text`, `evidenceIds`, `applicability`, `limits` | 어느 설명의 근거인지 추적; 숫자·효능·대상 확대는 사람 검토 |
| 운영 사실 참조 | `factId`, `displayContext` | 의학 논문을 병원 시간·가격의 근거로 사용하지 않음 |
| 실제 집필 표시 | `pageId`, `personId`, `role` | 실제 작성 역할이 확인된 경우만 author 표시 |
| 실제 검토 표시 | 기존 검토 기록 + `reviewerId` | 해당 인물·의료 역할·유효기간·digest와 공개 표시 일치 |
| 내부 작업 상태 | 미확정 사유·후보 조사 ID·원고 수정 요청 | 공개 렌더링 데이터에서 분리; 병원 사이트에는 표시하지 않음 |

학술 근거에는 대상·검사/처치·시점·결과·통계량 범위가 필요할 수 있다. 현재 범용 하네스의 모든 논문 범위 필드를 운영 출처에 억지로 채우지 말고 근거 유형별 계약을 설계한다. 입력 필드 일치는 실제 논문과 주장 일치의 증명이 아니므로 의료 검토 항목으로 남긴다.

환자에게는 해당 절 가까이에 무엇을 확인할 수 있는지 알 수 있는 출처 링크를 제공한다. 절 ID는 순번만으로 만들지 않고 변경에 강한 ID를 사용한다. 본문·출처 목록·JSON-LD citation은 같은 공개 출처 집합을 사용한다. 출처 탐색 메모·권리 검토 상태·내부 승인 증거는 React 직렬화 데이터에도 들어가지 않게 공개 필드를 명시적으로 골라 전달한다.

실제로 검토한 의료진의 이름과 검토일, 프로필을 해당 의료정보에 표시한다. 작성과 검토 역할이 다르면 구분한다. 의료진 프로필이 존재한다는 이유로 모든 글의 author로 지정하지 않는다. 정확한 집필자·프로필 연결은 Google의 사람 중심 콘텐츠 안내에도 포함된다. [작성자 정보 안내](https://developers.google.com/search/docs/fundamentals/creating-helpful-content#who-how-and-why).

`FAQPage` 추가를 합격 조건으로 삼지 않는다. Google은 2026-05-07부터 FAQ 리치 결과 표시를 중단했다고 공지했다. 질문·답변 HTML의 유용성은 계속 평가한다. `llms.txt`도 내부 보고서나 AI 전용 숨은 주장으로 채우지 않는다. [Google 변경 기록](https://developers.google.com/search/updates).

## 5. 기존 사이트와 병행 운영

T08에서 원 홈페이지의 현재 정보와 신규 원장을 대조한다. 이전 `/MAIN2`, `/33`의 검사 항목, `/38` 설명 혼입 등은 **재확인 대상**이며 현재도 그대로 남아 있다고 미리 확정하지 않는다. 병원명·전화·주소·시간·실제 의료진 정보를 함께 관리할 변경표를 만든다.

기존 사이트의 검사 소개에서 새 사이트의 준비·비교 설명으로 연결하고, 새 사이트에서는 원래 공지·사례로 연결하는 위치를 제안한다. 기존 사이트나 지도 계정의 실제 편집은 해당 작업 범위와 접근 권한이 확인된 실행 단계에서 수행한다. 문서 작성만으로 외부 변경이 완료됐다고 표시하지 않는다.

독립적인 새 안내는 자기 URL을 canonical로 쓴다. 실질적 복제 자료가 생기면 문서별 대표 URL을 판단한다. 병행 운영을 전체 301 이전이나 모든 새 페이지의 원 사이트 canonical로 처리하지 않는다. canonical은 검색엔진의 대표 문서 선택 신호이며 두 도메인의 동시 색인 보장이 아니다. [Google canonical 안내](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls).

## 6. 검증과 공개 순서

원고 변경에 맞는 기존 검사를 사용한다. 낮은 영향의 문구마다 구현을 복제한 테스트를 늘리지 않고, 새 데이터 계약·사실 전파·출처와 인물 참조·배포 경계에 필요한 검사를 추가한다.

| 검증 | 검증할 실패 사례 |
|---|---|
| 공통 사실 전파 | 메모리의 시험 데이터에서 전화·주소·시간 변경 후 화면·메타·JSON-LD·검색 텍스트에 옛 값이 남음 |
| 시간·위치 | 토요일에 평일 점심이 잘못 적용됨; 미확정 좌표 출력; 접수 마감을 영업 종료로 표시 |
| 주장·출처 참조 | 없는 근거 ID; 논문 대신 수요 조사 URL로 의료 주장 승인; 출처 범위 불일치 |
| 실제 인물·검토 | 다른 의사 프로필 연결; 승인 없는 author/reviewedBy; 원고 수정 후 낡은 digest |
| 정적·접근성 | JS가 없으면 추가 답변이 사라짐; 긴 표의 모바일 넘침; 절 링크·인쇄·키보드 회귀 |
| 내부 자료 경계 | 신규 원장의 내부 메모·질문 수요·개발 계획이 HTML/RSC/JSON/TXT/XML에 노출 |
| 관측 집계 | 원·신규 URL 중복 합산; 다른 저장소 URL 오인; 오류 응답을 성공률 분모에 포함 |

실행은 `web/`에서 현행 `npm run content:validate`, `npm run lint`, `npm run typecheck`, `npm test`, `npm run harness-check`, `npm run build`, `npm run audit:static`, `npm run test:e2e`를 변경 범위에 맞게 적용한다. 루트 및 GitHub 프로젝트 하위 경로를 기존 방식으로 검증한다. 콘텐츠 증가로 크기가 달라지는 홈·심장초음파·준비 안내·검색은 기존 성능 검사 체계로 대표 측정한다. 의료 정확성은 자동 검사 통과로 인증하지 않는다.

공개할 최종 원고에 실제 검토 기록이 갖춰지면 `npm run build:release`와 production 출력 감사를 통과시킨다. 그 전에는 review의 noindex를 유지한다. 일부 원고만 공개하려면 노출할 경로·탐색·사이트맵·기존 검토 게이트를 함께 검토하는 별도 변경으로 다루며, 실패를 피하려고 indexable 값을 일괄 바꾸지 않는다.

Actions는 검사 완료 후 `web/out/`만 GitHub Pages에 배포한다. 배포 후 같은 실행의 검사 artifact에 들어 있는 매니페스트와 공개 HTML을 대조한다. 현재 정리 작업에서 추가한 artifact 연계는 아직 GitHub 실행으로 확인되지 않았으므로 T11에서 실제 실행 로그로 검증해야 한다.

공개 예정 홈은 직전 감사에서 404였다. 배포 단계에서는 Pages 설정·실행 권한·정확한 주소·HTTPS 200·하위 경로 자산·존재하지 않는 URL의 404를 확인한다. 호스트 루트 robots 정책과 프로젝트 하위 `robots.txt`의 범위를 혼동하지 않는다. 공개 sitemap에는 실제 공개 가능한 canonical URL만 넣고 검색·404·내부 문서는 제외한다. 현재 후보 43개를 곧바로 색인 완료 수로 보고하지 않는다.

검색 관리자 등록·사이트맵 제출 뒤 실제 수집·색인·선택 canonical을 확인한다. 공개 HTTP 200과 sitemap 존재만으로 AI 인용 가능성이나 실제 노출을 완료 처리하지 않는다. 등록 후 확인할 성과 항목은 [측정안](measurement.ko.md)에 따른다.
