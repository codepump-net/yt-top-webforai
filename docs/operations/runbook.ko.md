# 운영·출판·배포 런북

기준일: 2026-11-16. 현재 워크플로와 코드 기준이다. [정책](../patient-content-policy.ko.md), [콘텐츠 계약](../architecture/content-model.ko.md), [검사 기준](../development/testing.ko.md)을 함께 사용한다.

## 1. 운영 경계

| 대상 | 운영 원칙 |
|---|---|
| 환자 사이트 | GitHub Pages에 `web/out/`만 배포 |
| 기존 병원 사이트 | 병행 운영하는 원문 채널. 이 프로젝트에서 수정하지 않음 |
| 검수·측정·문서 | 웹 출력 밖. 공개 저장소·artifact에도 비공개 증거를 넣지 않음 |
| Google·Naver·분석 계정 | 실제 권한이 있는 운영자만 확인. 태그 파일 게시와 계정 확인은 구분 |
| 운영자 앱 | 계획 단계. 환자 페이지에 임시 관리 화면을 만들지 않음 |

## 2. 공개 모드

| 항목 | review | production |
|---|---|---|
| 실행 | `npm run build` | `npm run build:release` |
| 용도 | 로컬·PR 검토 | 실제 공개 배포 |
| robots 메타 | 일반 페이지 noindex | 원장 indexable 대상 허용·예외 유지 |
| XML | 빈 공개 XML, 후보는 `reports/` | 허용 후보 132개(현재 원장 기준) |
| 공개 근거 | 원고 품질 검사는 유지 | 현재 범위·내용·렌더러·기간 확인 추가 |
| 분석 태그 | 삽입하지 않음 | 컴포넌트 삽입 후 도메인·URL 조건 추가 검사 |

현재 Actions의 main·수동 main 실행은 production, PR은 review다. 레거시 `PUBLICATION_MODE` 변수는 이 선택에 사용되지 않는다. 코드·로컬 산출물·실제 배포 상태를 각각 구분한다.

## 3. 배포 전 절차

1. 기능 명세·원고·근거·환자 목적·공통 사실의 변경 범위를 확인한다.
2. 실제 의료·운영 확인과 공개 권한이 현재 변경을 포괄하는지 확인한다. 단순 플래그·가짜 검토자·자동 확인 갱신으로 해결하지 않는다.
3. [변경별 검사](../development/testing.ko.md)를 수행하고 배포 변수·도메인·basePath를 확인한다.
4. 환자용 앱 변경을 main에 반영할 때 전체 CI와 production 검증이 실행되는 것을 확인한다.
5. 두 레이아웃 검사·배포·실제 대조까지 성공해야 배포 완료로 기록한다.

현재 사용자 도메인의 예상 설정은 `SITE_ORIGIN=https://yttop.kr`, root 배포용 `SITE_BASE_PATH=''` 또는 정규화되는 `/`다. CI의 repository variable이 없으면 origin은 기존 GitHub 호스트, project 경로는 `/yt-top-webforai`로 fallback한다. 실제 저장소 설정을 확인해야 하며 문서만으로 원격 값을 단정하지 않는다.

## 4. Actions 흐름

`pages.yml`의 root/project 행렬 각각 설치 → 의존성 감사 → lint·단위·Python 하네스 → 빌드·출력 감사 → 타입 → 브라우저·성능 검사를 수행한다. 두 검사가 성공한 후 project 레이아웃의 `out/`을 Pages에 배포한다. PR은 배포하지 않는다.

배포 전 원격 main과 실행 SHA가 같은지 확인해 오래된 실행을 거절한다. 배포 후 같은 실행의 `checks-project` artifact에서 매니페스트를 읽어 모든 HTML 해시·canonical·색인 지시·사이트맵·robots·HTTP 404를 확인한다. 매니페스트를 공개 사이트에 올리지 않는다. CI 보고 artifact의 보관 기간은 현재 30일이다.

## 5. 정기 점검 제안

아래 주기는 운영 제안이며 이미 예약 실행 중인 작업이라는 뜻은 아니다.

| 시점 | 담당 역할 | 점검 |
|---|---|---|
| 정보 변경 때 | 운영·콘텐츠 | 전화·시간·의료진·검사·서류·기간·근거 |
| 배포마다 | 개발·운영 | CI·실제 HTML·404·내부 파일 미노출 |
| 매주 | 콘텐츠·운영 | 기간 공지·깨진 중요 외부 링크·검색 계정 오류 |
| 매월 | 개발·운영 | 의존성·Node 지원·공개 근거 기간·docs 동기화·측정 한계 |
| 대규모 확장 전 | 제품·개발 | 분류·템플릿·호스팅 제약·백엔드 필요·ADR |

## 6. 장애별 대응

| 증상 | 먼저 확인 | 복구 방향 |
|---|---|---|
| production 검증 거절 | 실제 확인 범위·만료·내용·renderer digest | 정당한 증거 또는 내용 수정. gate 유지 |
| 검색 미노출 | 배포 모드·noindex·XML·canonical·계정의 실제 수집 상태 | 원인 교정 후 재배포·계정 관측 |
| 페이지·자산 404 | 원장·basePath·내보내기·경로 대소문자 | 원장에서 수정하고 재빌드 |
| 공지 기간 오류 | 한국 날짜·시작/종료·확인 기준일·빌드 시점 | 공식 조건 재확인·원장 갱신·재빌드 |
| 실제 HTML 불일치 | 같은 실행 매니페스트·SHA·배포 완료·캐시 | 의도한 릴리스 재검증. 성공으로 덮지 않음 |
| GA 보고서 비어 있음 | 태그 조건·실제 전송·컨테이너·cookieless 제약 | 미측정·제한으로 기록. 방문자 UI 추가 금지 |
| 의존성 감사 실패 | 현재 advisory·lockfile·예외 기한·네트워크 | 호환 수정·검증. 무기한 예외 금지 |

의학적으로 유해하거나 사실이 틀린 정보는 해당 안내의 노출 중단·수정 범위를 우선 판단하고 실제 책임자에게 확인한다. 환자 원문·검사자료는 문제 재현용으로도 공개 보고서에 넣지 않는다.

## 7. 복구와 인수 기록

정상 상태의 코드·내용을 복원하는 **새 커밋**을 main에 반영해 다시 검사·배포한다. 무조건 과거 workflow를 재실행하면 최신 SHA 방어에 막히거나 만료된 근거 문제가 남는다. 도메인·basePath가 바뀌면 새 설정으로 재빌드하고 확인 파일·robots·절대 URL을 점검한다.

기록에는 기능 ID·변경 SHA·실제 확인 범위·검사 실행·배포 실행·실제 대조·남은 문제를 넣는다. 배포 성공을 색인 완료·검색 상승·환자 방문 증가로 기록하지 않는다.
