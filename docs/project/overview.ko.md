# 프로젝트 개요와 문서 운영

기준일: 2026-11-16. 분석 기준 코드: `50412dc`(2026-11-08). 이 문서군은 저장소의 구현 분석과 향후 개발 기준이다. 운영 사이트의 현재 응답·검색 성과를 새로 실측한 보고서는 아니다.

## 1. 제품 정의

**TOP 건강백과는 영통탑내과가 운영하는 환자용 건강정보·병원 이용 안내 사이트다.** 증상 이해에서 검사 준비, 의료진 확인, 실제 방문까지 연결한다. 사이트 이름은 `content/site.json`, 병원 명칭·주소·전화·진료시간은 `content/clinic.json`이 기준이다.

| 구분 | 역할 |
|---|---|
| `https://yttop.kr/` | 이 프로젝트의 건강정보·진료·검사·방문 안내 |
| `https://yttop.co.kr/` | 병행 운영하는 기존 병원 홈페이지, 공지와 사례의 원 게시 채널 |
| 이 저장소의 `docs/` | 개발·운영·교육용 문서. 환자용 웹사이트의 메뉴나 페이지로 게시하지 않음 |

원 사이트 수정 권한을 전제로 하는 개발 과제를 만들지 않는다. 원 사이트에 링크를 추가하는 일도 이 프로젝트의 필수 후속 작업으로 두지 않는다.

## 3. 분석에서 드러난 구조적 특징

1. **데이터 중심 생성:** JSON 원고를 공통 렌더러가 화면·검색·SEO로 변환한다.
2. **공통 정책의 영향이 큼:** 분류 함수·CSS·렌더러 수정이 여러 경로에 전파된다. 기능별 작업에도 교차 검증이 필요하다.
3. **출판과 빌드가 분리됨:** 로컬 기본값은 review/noindex다. production은 실제 공개 확인 또는 개별 검토 기록을 검사한다.
4. **이력은 풍부하나 진입점이 부족했음:** 오래된 45·76·108페이지 문서와 review 배포 설명이 남아 있다. 날짜별 기록을 현재 명세로 오해하지 않도록 현행 문서군을 위에 둔다.
5. **확장은 작은 단위부터:** 약 1,000행의 `content.tsx`, 여러 곳에 놓인 페이지 타입·검증, 수동 분류를 향후 개선 후보로 삼는다. 이번 문서 작업에서 코드 구조를 변경하지는 않는다.

## 4. docs 폴더의 역할

| 폴더 | 질문 | 유지 책임의 권장 역할 |
|---|---|---|
| `project/` | 왜 만들며 어디까지 하는가? | 제품 책임자·개발 리드 |
| `product/` | 누구의 어떤 필요를 어느 경로에서 해결하는가? | 기획·콘텐츠 편집자 |
| `architecture/` | 데이터와 코드가 어떻게 연결되는가? | 개발자 |
| `design/` | 어떤 시각·상호작용 규칙을 따르는가? | 디자인·프런트엔드 |
| `seo/` | 어떻게 발견·해석·관측하는가? | 콘텐츠·SEO 담당 |
| `features/` | 기능별로 무엇을 수정하고 검증하는가? | 해당 작업 담당자 |
| `development/` | 어떻게 개발하고 완료를 판단하는가? | 개발자·검증 담당 |
| `operations/` | 배포·정기 점검·장애 대응은 어떻게 하는가? | 운영자 |
| `roadmap/` | 다음에 무엇을 어떤 순서로 하는가? | 제품 책임자·개발 리드 |
| `lectures/pwd-2026-2/lecture-09/` | 이 사례를 수업에서 어떻게 사용하는가? | 강의자·수강생 |
| `templates/`, `decisions/` | 새 기능·작업·의사결정을 어떻게 기록하는가? | 작업 제안자·검토자 |
| `tools/` | 경로와 수치 문서를 어떻게 동기화하는가? | 개발자 |
| `client-requests/` | 의뢰자가 무엇을 요청했고 어떻게 확인·반영했는가? | 요청서·관련 자료를 요청별로 보관하고 현행 명세와 연결 |

책임은 역할 제안이며 특정인의 실제 승인·의료 검토를 의미하지 않는다.

## 5. 기준의 우선순위와 문서 수명

프로젝트 범위는 `AGENTS.md`와 [환자용 콘텐츠 기준](../patient-content-policy.ko.md)을 따른다. 실제 경로·내용은 `content/pages.json`·`page-intents.json`, 구현 동작은 코드와 검사, 배포 사실은 해당 실행의 증거를 확인한다. 본 문서군과 코드가 어긋나면 원인을 조사해 명세·코드를 함께 정정한다.

`features/`는 현행 동작과 확장 후보를 구분한다. 신규 과제는 `roadmap/`에서 추적하고, 선택의 이유는 ADR로 남긴다. 의뢰자 요청서와 요청별 검토·반영 자료는 [client-requests/](../client-requests/README.md)에 모으고 새 날짜별 요청 폴더도 그 아래에 만든다. 공통 운영·개발 절차는 현행 주제별 문서에 반영한다. 과거 보고서의 실패·제약·승인 기록을 최신 성공 문장으로 덮어쓰지 않는다.

월 1회, 또는 경로·분류·빌드·배포 변경 PR마다 문서와 생성 인벤토리를 확인한다. 개인정보·비밀키·비공개 검수 원문은 내부 문서라는 이유로 공개 저장소에 넣지 않는다.
