## 우선 수정 P1

### UI-01. 짧은 화면에서 펼친 메뉴가 하단 바·뷰포트에 가려짐

**영향:** 공통 헤더를 사용하는 전체 페이지. 특히 모바일 가로 방향과 확대 후 높이가 짧아진 창.

**재현:** 홈을 600×320px로 열고 메뉴를 펼칩니다. 마지막 행의 `공지사항`, `전체 페이지` 중심점 y=307.9px을 하단 연락 바가 덮습니다. 본문을 아래로 스크롤해도 중심점 y=276.9px이 연락 바 영역 y=265~320px 안에 남습니다. 링크에 포커스를 주어도 해소되지 않습니다. 320×225px 상당 크기에서는 아래 4개 메뉴의 중심점이 접근 불가하며, 844×256px에서도 마지막 행이 화면 밖에 남습니다.

**원인:** 메뉴는 sticky 헤더 아래 `position:absolute; top:100%`로 고정되는데 높이 제한과 내부 세로 스크롤이 없습니다. 헤더 z-index 40보다 하단 바의 z-index 45가 높습니다. 폭 조건만 있고 짧은 높이 대응이 없습니다.

**수정 방향:** 펼친 메뉴의 높이를 실제 가용 뷰포트에 맞추고 내부 스크롤을 제공해야 합니다. 헤더·하단 바·안전 영역을 함께 계산하고 메뉴가 열린 동안의 가림 순서를 정합니다. z-index만 높여 마지막 행을 화면 밖에 남기는 수정은 불충분합니다.

**완료 조건:** 320×225, 600×280, 600×320, 844×256에서 모든 항목을 터치·Tab으로 찾아 선택할 수 있고, 메뉴 안에서 끝까지 스크롤할 수 있어야 합니다.

위치: [globals.css](../web/src/app/globals.css) 1250행의 모바일 메뉴 규칙, 1931행의 하단 바. [chrome.tsx](../web/src/components/chrome.tsx) 34행.

증거: [600×320 메뉴](../artifacts/ui-audit-2026-09-11/screenshots/menu-600x320.png), [320×225 메뉴](../artifacts/ui-audit-2026-09-11/screenshots/menu-zoom-equivalent-320x225.png).

### UI-02. Tab 이동 시 포커스된 링크가 하단 고정 바 뒤에 완전히 가려짐

**영향:** 하단 바가 표시되는 600px 이하 화면. 홈·심장초음파·검색에서 실제 Tab 순서로 재현했습니다.

**재현:** 390×844px 홈에서 Tab으로 `031-202-7555` 링크에 이동하면 링크는 y=799.8~830.6px에 놓이고, 하단 바는 y=789~844px를 차지합니다. 링크와 포커스 표시가 모두 바 뒤로 들어갑니다. 홈의 `방문 안내 보기`와 상세 페이지 푸터의 `진료시간·위치`, `비용·서류`도 재현됩니다.

**원인:** 푸터의 아래 여백은 문서 맨 끝을 보호하지만, 브라우저의 개별 포커스 스크롤에는 하단 고정 바 높이가 반영되지 않습니다. 전역 `scroll-padding-top`만 설정돼 있습니다.

**수정 방향:** 하단 바와 안전 영역을 고려한 `scroll-padding-bottom` 및 필요한 포커스 대상의 스크롤 여백을 적용하고, 실제 Tab 이동으로 재검증합니다. 헤더 가림도 함께 확인합니다.

**완료 조건:** 홈·상세·검색의 처음부터 끝까지 Tab/Shift+Tab으로 이동할 때 현재 조작 대상과 포커스 표시를 확인할 수 있어야 합니다. 이는 [W3C Focus Not Obscured 설명](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html)의 핵심 확인 항목입니다. 자동 axe 통과가 이 문제의 부재를 의미하지 않습니다.

위치: [globals.css](../web/src/app/globals.css) 19행, 1931행.

증거: [홈 전화 링크 포커스](../artifacts/ui-audit-2026-09-11/screenshots/keyboard-home-1.png), [홈 방문 버튼 포커스](../artifacts/ui-audit-2026-09-11/screenshots/keyboard-home-2.png), [상세 푸터 링크 포커스](../artifacts/ui-audit-2026-09-11/screenshots/keyboard-echocardiography-2.png). 해당 순간의 포커스 대상·좌표는 `interactions.json`의 `keyboard`에 있습니다. 푸터 로고처럼 inline 요소의 빈 영역을 중심점으로 잡은 후보는 결함 판정에서 제외했습니다.

### UI-03. 검색어와 제목이 직접 일치하는 검사 안내가 마지막에 표시됨

`심장초음파` 검색에서 `심장초음파 검사`가 **10개 중 10번째**, `대장내시경` 검색에서 해당 검사 페이지가 **7개 중 7번째**입니다. 앞에는 사례 글이 먼저 표시됩니다. 반면 `진료시간`은 1개 결과로 정상 탐색됩니다.

검색은 입력·필터·결과 표시 자체는 작동하지만, 환자가 검사 목적과 준비를 빠르게 찾는 목적에 맞는 정렬이 없습니다. `items.filter()`가 원본 데이터 순서를 유지하며, 명세에 있던 제목 우선 가중치가 구현되지 않았습니다.

수정 방향은 제목의 정확한 일치·제목 포함·설명/질문 일치·본문 일치 순으로 정렬하는 것입니다. 적어도 두 검사어의 직접 안내가 상위에 나타나는지 확인해야 합니다.

위치: [search.tsx](../web/src/components/search.tsx) 24~42행. [검색 설계](implementation-plan/execution-plan.ko.md)의 정적 검색 명세.

증거: [심장초음파 검색 첫 화면](../artifacts/ui-audit-2026-09-11/screenshots/search-ranked-1.png), `supplement.json`의 `search`에 전체 상위 결과와 순위 기록.

### UI-04. 인쇄·PDF에서 접힌 Q&A 답변이 누락됨

대장내시경 준비 페이지를 초기 상태 그대로 인쇄하면 첫 질문 답변만 출력되고, `정결제를 먹기 어렵다면 어떻게 하나요?`, `복용약이나 기존 질환을 알려야 하나요?`에는 질문만 남습니다. 실제 A4 PDF와 추출 텍스트로 확인했습니다. 준비 정보를 보관·공유하려는 사용자가 펼침 여부에 따라 다른 문서를 받게 됩니다.

현재 `@media print`에서 답변에 `display:block`을 주지만 native `details`의 닫힌 콘텐츠까지 열리지 않습니다. Q&A를 가진 25페이지가 같은 컴포넌트를 사용하므로 공통 수정 대상입니다. PDF 재현 검사는 대표 준비 페이지에서 수행했습니다.

수정 방향은 인쇄 시 모든 답변이 확실히 렌더링되도록 처리하고, 인쇄 종료 후 원래 펼침 상태를 보존하는 것입니다. `::details-content` 대응 또는 beforeprint/afterprint 처리 등 구현을 정한 뒤 실제 PDF 내용으로 검증해야 합니다.

위치: [content.tsx](../web/src/components/content.tsx) 368행, [globals.css](../web/src/app/globals.css) 2042~2071행.

증거: [생성 PDF](../artifacts/ui-audit-2026-09-11/preparation-print.pdf), [PDF 마지막 페이지](../artifacts/ui-audit-2026-09-11/screenshots/print-last-page.png), [추출 텍스트](../artifacts/ui-audit-2026-09-11/preparation-print.txt).

### UI-05. 601~850px 상세 화면에서 전화 문의 경로가 푸터에만 남음

심장초음파 상세 페이지에서 600px에는 하단 전화 바가 표시되지만, **601px이 되는 순간** 사라집니다. 헤더 전화 버튼은 1100px 이하에서 숨겨지고, 본문 문의 박스도 850px 이하에서 숨겨집니다. 따라서 601~850px에서는 전화 링크가 페이지 하단 푸터에만 남습니다. 601px 검사에서 그 위치는 문서 y≈3003px입니다.

홈·방문 페이지에는 본문 전화 정보가 있으므로 같은 정도의 문제는 아닙니다. 검사 안내를 직접 열고 문의하려는 태블릿 사용자의 경로가 특히 길어집니다. 이는 전화 기능 소실이 아닌 **주요 행동의 발견성 문제**입니다.

수정 방향은 헤더의 전화 아이콘 또는 본문 끝의 문의 버튼 등 일관된 대체 경로를 제공하는 것입니다. 응급 맥락 글에는 현재의 별도 문의 CTA 제외 정책을 유지해야 합니다.

위치: [globals.css](../web/src/app/globals.css) 1211행, 1401행, 1931행; [content.tsx](../web/src/components/content.tsx) 391행.

증거: [768px 검사 상세](../artifacts/ui-audit-2026-09-11/screenshots/tablet-detail-768.png), `supplement.json`의 `contact`.

### UI-06. 병원 이용에 중요한 정보의 글자가 작고, 좁은 시간표가 부자연스럽게 줄바꿈됨

홈 모바일 진료시간·점심시간·접수 관련 안내가 **10px**, 방문 페이지 일반 설명은 12~13px, 상세 본문은 모바일 15px·데스크톱 16px입니다. 프로젝트 명세의 본문 17~18px 목표보다 작습니다. 320px 홈에서는 두 열을 유지한 시간표의 `점심시간`과 `13:00 – 14:00`이 각각 여러 줄로 갈라집니다.

문자 클리핑은 없지만, 병원 방문에 필요한 정보를 읽고 시간과 요일을 대응시키는 부담이 큽니다. 특히 작은 글씨를 확대해야 하는 사용자에게 중요합니다. 글꼴 크기만으로 WCAG 위반을 단정하지는 않습니다.

수정 방향은 진료시간·예약 조건을 주요 본문 수준으로 키우고 좁은 폭에서는 연락처와 시간표를 한 열로 재배치하는 것입니다. 확대 후에도 요일·시간의 대응이 유지돼야 합니다. 부가 메타데이터와 핵심 안내를 동일하게 작게 처리하지 않아야 합니다.

위치: [globals.css](../web/src/app/globals.css) 1557~1578행, 본문·방문 정보의 글꼴 규칙; [화면 명세](website-spec.ko.md) 139~143행.

증거: [320px 홈 연락처·시간표](../artifacts/ui-audit-2026-09-11/screenshots/home-contact-320.png), `supplement.json`의 `typography`.

### UI-07. 높이가 낮은 데스크톱 창에서 sticky 본문 문의 영역이 화면 밖에 머묾

1280×450px 심장초음파 상세에서 본문을 스크롤하면 사이드바가 y=120px에 고정됩니다. 높이는 약397px이므로 아래쪽이 y≈517px까지 내려갑니다. `진료시간·오시는 길` 링크 중심점 y≈480px이 화면 밖에 남습니다. 1024×600, 1280×720, 1920×1080에서는 재현되지 않았습니다.

본문의 끝에 가까워지면 sticky 컨테이너 제약으로 위치가 달라질 수 있으므로 영구적인 접근 불능으로 판정하지 않습니다. 다만 본문을 읽는 동안 문의 영역을 고정해 두려는 의도에는 맞지 않습니다. 사이드바를 사용하는 페이지는 60개이며 실제 높이는 항목 수에 따라 다릅니다.

수정 방향은 짧은 높이에서는 sticky를 해제하거나, 남는 높이에 맞춘 내부 스크롤·축소된 문의 박스를 제공하는 것입니다.

위치: [globals.css](../web/src/app/globals.css) 737행.

증거: [1280×450 사이드바](../artifacts/ui-audit-2026-09-11/screenshots/sidebar-1280x450.png), `interactions.json`의 `sidebar`.

### UI-08. 빈 검색 결과 초기화 후 키보드 포커스가 사라짐

사이트 검색과 사례 검색에서 결과가 없는 단어를 입력하고 `전체 목록 보기`를 누르면 목록은 정상 복원됩니다. 그러나 버튼 자신이 DOM에서 제거되면서 `document.activeElement`가 **BODY**로 바뀝니다. 320·390·768·1280px 모두 재현됩니다.

키보드 사용자는 다음 입력이나 결과 탐색을 어디서 이어갈지 알기 어렵습니다. 결과 개수의 live region만으로 포커스 위치까지 복구되지는 않습니다.

수정 방향은 초기화 후 검색 입력 또는 의도한 결과 시작 지점으로 포커스를 이동시키는 것입니다. 키보드 Enter로 초기화한 다음 즉시 새 검색어를 입력할 수 있는지 확인합니다.

위치: [search.tsx](../web/src/components/search.tsx) 97~108행.

증거: `interactions.json`의 `search[*].focusAfterReset` 8개 모두 BODY, `restored`는 모두 true.

## 배치·조작 품질 개선 P3

### UI-09. 글자 200%에서 의료진 이름과 주요 메뉴가 지나치게 분절됨

390px에서 글자를 200%로 키우면 의료진 카드가 사진 43%·설명 57%를 유지합니다. 이름과 직함을 같은 flex 행에 두기 때문에 `박종설`이 한 글자씩 3줄로 분리되고 해당 제목 영역의 높이가 약194px까지 늘어납니다. 1280px 헤더에서도 `의료/진`, `건강검/진`처럼 메뉴가 어중간하게 끊깁니다.

텍스트가 사라지는 문제는 아니지만 확대 사용자의 읽기 흐름이 나빠집니다. 사진과 설명을 세로로 배치하거나 이름·직함을 서로 다른 행으로 나누고, 메뉴는 가용 폭에 맞는 대체 배치를 검토하는 편이 좋습니다.

위치: [globals.css](../web/src/app/globals.css) 523·565·1664행 부근, [content.tsx](../web/src/components/content.tsx) 96행.

증거: [390px 의료진 글자 200%](../artifacts/ui-audit-2026-09-11/screenshots/doctors-390-text-200.png), [1280px 헤더 글자 200%](../artifacts/ui-audit-2026-09-11/screenshots/header-text200-1280.png).

### UI-10. 일부 독립 링크·필터가 프로젝트의 44px 조작 영역 목표보다 작음

390px 홈에서 전화번호 링크 높이는 약30.8px, 지도 링크는 21px, 섹션의 `전체 보기` 링크는 약19.3px입니다. 푸터 주요 링크는 약39.3px, 검색 분야 버튼은 42px입니다. 반면 검색·메뉴 아이콘은 44×44px, 하단 전화·위치 바는 높이55px로 충분합니다.

클릭되는 카드 안의 `자세히 보기` 텍스트는 카드 전체가 실제 링크이므로 작은 별도 타깃으로 세지 않았습니다. 본문 안 링크와 독립 조작 링크도 구분해야 합니다.

수정 방향은 독립적으로 자주 사용하는 전화·지도·필터·전체 보기 링크에 패딩과 최소 높이를 주는 것입니다. 44px는 **이 프로젝트 목표**입니다. WCAG 2.2 AA의 24px 최소·간격 예외와 혼동해 모든 44px 미만 항목을 규정 위반으로 판정하지 않았습니다. [W3C Target Size Minimum 설명](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)

위치: [globals.css](../web/src/app/globals.css)의 `.text-link`, `.phone-number`, `.filter-row button`, `.footer-links a`.

증거: `matrix.json`의 `smallTargets`는 수동 판별 전 후보 목록이며, 위 수치는 실제 개별 타깃에서 확인한 값입니다.

## 수정 순서와 재검증 기준

1. **메뉴·포커스 가림부터 수정:** 320×225, 600×320과 기본 390×844에서 모든 링크를 키보드·포인터로 확인합니다. 가로 스크롤 검사만 반복하는 것으로 끝내지 않습니다.
