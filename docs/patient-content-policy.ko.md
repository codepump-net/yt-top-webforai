# 환자용 병원 홈페이지 콘텐츠 기준

적용일: 2026-09-11. **개발·운영 내부 문서이며 웹사이트의 페이지로 게시하지 않는다.** 기존 사전 계획에 다른 지시가 있으면 이 기준과 현재 `content/pages.json`을 우선한다.

## 사이트의 목적과 독자

이 사이트는 영통탑내과를 소개하고, 실제 환자가 진료·검사·검진을 이해하며 병원을 방문하도록 돕는 병원 홈페이지다. 기존 `https://yttop.co.kr/`과 함께 운영한다. 환자에게 읽히는 정확한 정보를 검색엔진과 AI 모델도 이해하도록 정적 HTML과 메타데이터를 구성한다.

페이지 수, 개발 작업량, 검색 최적화 방법이나 검수 체계를 보여주는 것이 제품의 목적이 아니다. 환자에게 필요한 내용이 없는 페이지를 AI 노출만을 이유로 만들지 않는다. AI 전용으로 숨긴 주장이나 환자 본문과 다른 답변도 만들지 않는다.

## 페이지를 추가하거나 수정할 때

1. “환자가 이 페이지에서 무엇을 이해하거나 할 수 있는가?”를 한 문장으로 정의하고 `content/page-intents.json`에 경로와 함께 기록한다. 이 파일은 내부 판단 원장이며 공개하지 않는다.
2. 기존 페이지의 설명 보완, 관련 안내 링크 또는 기존 홈페이지 게시판 연결로 충분한지 먼저 판단한다. 새로운 키워드나 개발 계획의 항목 하나가 독립 페이지의 근거가 되지 않는다.
3. 병원 사실·검사 설명·진료 준비 등 실제 근거가 있는 내용을 쓴다. 소스의 모순, 미확인 사실, 편집 과정은 내부 기록에 남기고 환자에게는 확인할 대상과 문의 방법을 안내한다. 불확실한 수치·가격·현재 직책·의학적 결론을 임의로 확정하지 않는다.
4. 환자에게 유용한 검사 한계, 응급 증상 안내, 약 복용에 대한 개별 상담 필요성, 외부 서비스 개인정보 안내는 유지한다. 이런 안내를 개발 문구로 오인해 지우지 않는다.
5. 제목·요약·본문·질문·출처·이미지 설명뿐 아니라 메뉴, 푸터, 검색 결과, 구조화 데이터까지 같은 기준으로 읽어본다. 문구 검사 통과가 편집 판단을 대신하지는 않는다.

| 공개할 수 있는 내용 | 내부 문서에만 둘 내용 |
|---|---|
| 병원 소개, 의료진의 근거 있는 이력, 진료 분야 | 개발 진행률, 기술 선택, 페이지 생성 방법 |
| 검사 목적·준비·결과 이해, 진료 상담 질문 | 크롤링·OCR·자료 정규화·질문 선정 과정 |
| 전화·위치·진료시간·서류 및 비용 확인 방법 | 검수 대기 현황, 증거 원장, 승인 절차, 향후 계획 |
| 확인 가능한 참고 출처, 실제 검토자 표시 | 실행 사실이 없는 검수·정정 체계의 선언 |
| 검색·사이트맵·개인정보 등 사이트 이용 기능 | 검색 순위·AI 인용 관측 보고서와 성공 주장 |

실제 검토 기록이 생긴 경우 해당 의료정보에 이름과 검토일을 표시할 수 있다. 별도의 “작성·검수 원칙” 페이지를 자동으로 만들지 않는다. 실제로 시행하는 정책을 공개해야 하는 별도 필요가 생기면 그 필요와 사실 여부부터 판단한다.

## 문구 교정의 기준

| 제작 과정 중심의 잘못된 문구 | 환자에게 필요한 안내 |
|---|---|
| 기존 안내 간 항목 표기가 달라 확정되지 않은 검사 목록은 싣지 않았습니다. | 제출처에서 요구하는 검사 목록을 알려주세요. 검사 가능 여부와 결과지 발급일을 방문 전에 확인할 수 있습니다. |
| 기존 이벤트 가격을 상시 총 검사비로 안내하지 않습니다. | 검사비에 포함되는 항목과 별도로 발생할 수 있는 비용을 예약할 때 확인해 주세요. |
| 기존 자료를 정리한 검토용 안내이며 의료진 최종 검수 전입니다. | 이 상태는 내부 검수 원장에 기록한다. 환자 본문에는 검사 설명과 개인별 상담에 필요한 안내를 쓴다. |

개발 상태 문구를 없애는 것이 의료적 승인이나 검색 공개를 의미하지 않는다. 실제 승인 자료가 없는 동안에는 기존 `review` 빌드의 `noindex`와 production 검증을 유지한다. 승인을 받았다고 꾸미거나 자동으로 검토자 이름을 생성하지 않는다.

## 기존 홈페이지와 함께 운영하는 방법

- 기존 홈페이지는 공지와 진단 사례의 원 게시 채널로 유지한다. 신규 사이트의 `/notices/`는 공지 게시판, `/cases/`는 사례별 원문으로 연결한다. 기존 홈페이지를 폐쇄하거나 URL을 일괄 이전하는 계획을 기본값으로 두지 않는다.
- 신규 사이트는 병원 소개, 진료 목적별 안내, 검사 준비, 질문과 답변, 방문 동선을 제공한다. 동일한 병원명·전화·주소를 사용한다. 변경 시 양쪽 정보를 함께 확인한다.
- `MedicalClinic`은 기존 병원 URL 기반 ID를 사용하고 신규 `WebSite`와 페이지의 ID는 신규 주소로 구분한다. 이는 동일 병원을 명확하게 설명하기 위한 구현 선택이며, AI 인용이나 병원 인식 결과를 보장하지 않는다.
- 독립적인 환자 안내 페이지는 자기 URL을 canonical로 사용한다. 향후 실질적으로 같은 문서를 복제하는 경우에는 해당 문서의 대표 URL을 별도로 판단한다. canonical은 중복·유사 문서를 통합하는 신호이며, 두 사이트를 모두 색인하라는 지시가 아니다. [Google canonical 안내](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls).

Google의 AI 검색 안내는 일반 SEO 원칙, 유용한 정보, 텍스트 접근성, 본문과 일치하는 구조화 데이터를 강조하며 별도의 AI 전용 파일이나 특수 마크업을 요구하지 않는다. 이를 근거로 환자에게 도움이 없는 작성 원칙 페이지의 필요성이나 최적화 효과를 주장하지 않는다. 이는 Google에 대한 공식 안내이며 다른 AI 서비스 전체의 동일한 동작을 증명하지는 않는다. [Google AI 검색 안내](https://developers.google.com/search/docs/appearance/ai-features).

## 자동 검사와 배포 경계

- 데이터 검사: 페이지 목적 원장 누락, 폐기한 템플릿 복원, 제목·본문·질문·출처·사례 링크의 내부 보고 문구를 거절한다.
- 결과물 검사: 모든 HTML, React가 직렬화한 텍스트, JSON·XML·TXT를 읽고 내부 문구와 내부 파일 유출을 검사한다. 링크·메타데이터·병원 식별 정보도 검사한다.
- 공개 폴더: `web/out/`에는 환자용 사이트와 필요한 정적 리소스만 둔다. 빌드 매니페스트와 계획용 사이트맵은 `web/reports/`에 생성한다. 실제 공개용 `sitemap.xml`, `robots.txt`와 선택적 `llms.txt`는 별개의 탐색 파일이다.
- 배포: Actions는 `web/out/`만 배포한다. 배포 후 HTML 비교에 쓰는 매니페스트는 같은 실행의 검사 artifact에서 가져온다. 공개 사이트에 개발 보고서를 다시 올리지 않는다.
- 검토 기록과 조사 자료는 웹 출력에서 분리한다. 저장소의 `docs/`가 공개되어 있다는 사실과 병원 사이트에 게시한다는 것은 구분하며, 개인정보나 비공개 검수 증거는 공개 저장소에도 넣지 않는다.

검색 노출 전까지의 noindex는 접근 통제가 아니다. Google AI 검색의 출처 링크 자격에는 색인과 검색 스니펫 노출 가능성이 필요하므로, 현재 검토 모드의 기술적 준비 상태를 실제 AI 노출 성과로 보고하지 않는다. [Google AI 검색의 기술 요건](https://developers.google.com/search/docs/appearance/ai-features#technical-requirements).
