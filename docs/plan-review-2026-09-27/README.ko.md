**수정 방향:** 이 파일들을 실제로 제공할 때까지 문서 상태를 ‘설계안’으로 표시한다. 기존 파일→수정 파일 대응표와 실행 가능한 스크립트가 갖춰진 뒤 적용 절차를 확정한다. DOCX가 주장하는 신규 18개·기존 11개 패치는 ID와 영문 URL별 목록으로 증명해야 한다.

### 3. [높음] 제안한 데이터 필드와 이식 절차가 현재 콘텐츠 계약을 다루지 않는다

**위치:** 이식 README 51~60행; 통합안 MD 182~194행.

README는 페이지별 `footerVariant` 사용을 지시하지만 현재 `pageSchema`에는 이 필드가 없고 `.strict()`로 미등록 필드를 거절한다. 유효한 현재 페이지에 `footerVariant: 'medical'`만 추가한 메모리상 검사를 실행했을 때 스키마 검증이 실패했다. 현재는 `articleGuidance(page)`가 주제·경로를 기준으로 하단 안내를 결정한다.

신규 페이지에는 `page-intents.json`의 환자 목적 기록도 필요하다. 새로운 규칙·컴포넌트·검색 별칭 파일을 도입한다면 공개 승인 유효성을 판단하는 `rendererDigest` 입력에도 포함해야 한다. 단순히 새 파일을 넣고 렌더러에서 import하는 것만으로 이 계약이 완성되지는 않는다.

근거: [엄격한 페이지 스키마](../../web/scripts/content-contract.mjs), [페이지 목적 검사](../../web/scripts/public-content-policy.mjs), [렌더러 digest 대상](../../web/scripts/data.mjs).

**수정 방향:** 기존 하단 규칙을 확장할지 새 필드를 도입할지 먼저 정한다. 새 필드를 도입하면 타입·스키마·렌더링·회귀 검사까지 같은 변경 범위로 명시한다. 새 경로·이미지에는 목적 원장·에셋 원장·출처를 포함한다. 기존 공개 승인 digest를 자동 갱신하는 방식은 사용하지 않는다. 미제공 스크립트가 실제로 어떤 필드를 쓰는지는 이번 검토로 판단하지 않았다.

### 4. [중간] DOCX와 Markdown의 요구사항이 달라 완료 판정이 갈린다

**위치:** DOCX 5·8·9·10·11절, 통합안 MD 10~14절, 이식 README 54·60행.

| 요구사항 | DOCX | 통합안 Markdown |
|---|---|---|
| 목차 | DOM 1개, 상위 소제목 최대 8개, FAQ·참고자료·관련 글·주소 제외 | `UnifiedToc.tsx` 파일명만 열거 |
| 검색 초기 상태 | 검색 전 전체 목록을 나열하지 않음, 개인정보 입력 금지 안내 | 해당 기준 없음 |
| 만성질환·금연치료 | 별도 절, 공단 금연치료 지원사업 참여 명시 | 진료분야 표의 항목 수준 |
| 사례 robots | `noindex·nosnippet·noimageindex` | `nofollow`도 포함 |
| 신규·수정 수량 | 신규 18개·기존 11개 | 수량과 ID·URL 목록 없음 |

현재 목차는 **하나의 React 컴포넌트가 같은 내용을 PC·모바일 DOM에 각각 출력**하고 CSS로 전환한다. 심부전 페이지에서 목차 내용 DOM은 2개이고 각 목차의 항목은 17개다. 실제 브라우저에서 PC용과 모바일용이 동시에 노출되지는 않았고, 모바일 펼침과 가로 넘침 여부도 정상 확인했다. 따라서 ‘DOM 1개’는 아직 구현되지 않은 새 요구사항이며 현재 화면의 중복 노출 버그로 단정할 수 없다.

근거: [현재 목차](../../web/src/components/article-navigation.tsx), [목차 항목 생성](../../web/src/components/content.tsx), [반응형 스타일](../../web/src/app/globals.css).

**수정 방향:** 하나의 요구사항 원본을 정하고 다른 형식에도 동일하게 반영한다. 목차에서 FAQ·출처로 가는 길을 줄이는 변경은 환자의 탐색 요구와 함께 판단한다. 목차를 개편할 경우 모바일 접기, 키보드 이동, 자바스크립트 없는 탐색, 번역·인쇄 동작을 완료 조건에 명시한다.

### 5. [중간] 사례 정책은 원문 연결 보존과 탐색 제외 범위를 구분해야 한다

**위치:** 통합안 MD 156~166행, 이식 README 44~45·59·75행; DOCX 10절.

현재 `/cases/`는 실제 환자 상세 글을 새 사이트에 복제한 페이지가 아니라 **기존 병원 사례 원문 25개로 연결하는 목록**이다. 일반 사이트 검색에는 `/cases/` 목록 1개가 들어가고, 사례 25개 검색은 그 목록 페이지 안에서 따로 제공한다. HTML 사이트맵과 병원안내 허브에도 목록 링크가 있다. 현재 review 출력은 `noindex, follow`이며 데이터의 `indexable`은 `true`다.

[현재 정책](../patient-content-policy.ko.md)은 원문 연결을 보존하도록 한다. 검색·사이트맵에서 목록의 노출을 줄이는 제안 자체가 원문 연결 삭제를 요구하는 것은 아니다. 문서에는 `/cases/`를 유지하는지, 페이지 안의 사례 검색도 없애는지, 외부 원문 링크를 어디서 계속 제공할지를 명시해야 한다. 교육용 복합 사례 제안을 과거에 폐기한 사례 상세 복제 페이지의 복원으로 해석해서는 안 된다.

또한 현재 코드는 `indexable=false`만으로 계획의 전체 제외 조건을 만족하지 않는다. HTML 사이트맵은 별도 그룹 함수를 사용하고, `/cases/`의 JSON-LD에는 원문 25개가 `ItemList`로 포함된다. production의 선택적 `llms.txt` 생성과 병원안내 메뉴도 영향 범위다. `noindex`를 접근 통제로 취급하지 않는 현재 정책을 유지해야 한다.

근거: [사례 원문 원장](../../content/case-links.json), [사례 목록 렌더링](../../web/src/components/content.tsx), [사이트맵 그룹](../../web/src/lib/information-architecture.mjs), [JSON-LD](../../web/src/lib/structured-data.mjs), [공개 탐색 파일 생성](../../web/scripts/build.mjs).

**수정 방향:** ‘사례 삭제’와 ‘신규 사이트의 검색 노출 제외’를 분리해 대상별로 명세한다. 개인정보 안내의 운영 원칙도 실제 운영 범위를 근거로 작성한다. 이번 검토는 기존 외부 원문의 환자 동의나 비식별 상태를 새로 확인한 것이 아니다.

### 6. [중간] “같은 원장”과 “모든 화면에 같은 목록”을 구분해야 한다

**위치:** 통합안 MD 124·168~180·194행; DOCX 1·7·12절.

현재 HTML 사이트맵은 404를 제외한 93개, 사이트 검색은 91개, 질환백과는 28개다. 이 차이는 각 화면의 목적과 필터 때문이며 원장이 다르다는 증거가 아니다. 관련 글 역시 주제별 선택이므로 모든 상세 페이지에 심장·혈관 20편 전체를 반복할 필요는 없다.

review 모드의 공개 XML 사이트맵은 의도적으로 0개다. 후보 URL은 공개 폴더 밖의 `web/reports/planned-sitemap.xml`에 기록한다. 공개 XML을 HTML 목록과 강제로 맞추면 기존 검토 모드 검사에 어긋난다.

**수정 방향:** 완료 조건을 ‘같은 원장에서 목적·공개 모드별로 선택한 결과가 올바름’으로 작성한다. review에서 공개 XML 0개, HTML 탐색 정상, production은 실제 승인과 해당 경로의 색인 정책을 모두 만족하는 항목만 포함하는 기준을 유지한다.

### 7. [중간] 예방접종 시각자료와 신규 병원 운영 사실의 근거 작업이 빠져 있다

**위치:** 통합안 MD 98~102행; DOCX 5·6절; 이식 README 42~47행.

현재 예방접종 페이지에는 접종 종류별 설명과 출처가 있지만 본문 이미지·HTML 표는 각각 0개다. DOCX 안의 일정표는 구현에 활용할 시각자료 후보이며, 웹용 에셋 등록과 동일한 HTML 표 작성은 남아 있다.

이미지의 A형간염 일정은 `0, 6~12개월`이고 현재 본문은 제품에 따라 `6~18개월 간격`이라고 설명한다. 어느 쪽을 의학적으로 확정하는 검토는 하지 않았다. 이미지·표·본문의 조건과 표현을 같은 기준으로 정리해야 한다는 대조 결과다. 이미지 하단의 기관명과 ‘최신 공개 자료 기준’만으로 특정 판본·대상·확인일이 명확해지는 것도 아니다.

DOCX의 ‘국민건강보험공단 금연치료 지원사업 참여’는 현재 코드·콘텐츠·검토한 구현 기록에서 근거를 확인하지 못한 병원 운영 사실이다. 공식 영문명도 현재 화면의 `YEONGTONG TOP CLINIC`과 새 요청의 `YEONGTONG TOP INTERNAL MEDICINE CLINIC`이 다르다. 이들은 구현 여부와 실제 사실 확인을 구분해 기록해야 한다.

**수정 방향:** 예방접종 표의 항목별 출처와 적용 조건, 이미지 제작·사용 근거, 금연치료 지원사업 참여 확인 근거를 작업에 포함한다. 영문명이 확정되면 홈·푸터·로고 등 적용 범위를 정한다. 자료 제출 자체를 웹 편집본의 의료 검토 완료로 표시하지 않는다.

## 실행 문서로 바꿀 때 권장하는 순서

1. 첫 절을 현재 구현 현황으로 갱신하고 위 표의 유지·수정·추가 항목을 작업 목록으로 전환한다. DOCX와 Markdown의 추가 요구사항을 통일한다.
2. 신규·수정 대상별 `id`, 영문 `path`, 기존 대응 페이지, 환자 목적, 출처, 연결할 허브를 기록한다. 간질환·경동맥질환·암환자 지지진료처럼 기존 안내가 있는 영역은 중복 페이지 생성부터 하지 않는다. 현 단계에서 총 경로 수를 94+18로 확정할 근거는 부족하다.
3. 기존 `information-architecture.mjs`, `article-guidance.mjs`, `article-footer.tsx`, `article-navigation.tsx`, `search.tsx`의 역할을 기준으로 변경 파일을 정한다. 새 이름의 유사 컴포넌트를 별도로 연결하는 작업으로 표현하지 않는다.
4. 병원 운영 사실·예방접종 표 근거를 확인하고, 콘텐츠 계약·목적 원장·에셋 원장·렌더러 digest 반영까지 구현 범위에 넣는다.
5. 아래 검증을 Node.js 24에서 수행한다. 실제 신규 구현 전에는 이번 기존 코드 검사의 통과를 새 계획의 완료로 사용하지 않는다.

```bash
cd web
npm run content:validate
npm test
npm run lint
npm run typecheck
PYTHON=python3 npm run harness-check
npm run build
npm run test:e2e
SITE_ORIGIN=https://codepump-net.github.io SITE_BASE_PATH=/yt-top-webforai npm run build
npm run test:e2e
```

`npm run build`는 자체적으로 정적 출력 감사를 실행한다. 변경 후에는 신규 진료 구조·예방접종 표·검색·목차·사례 정책의 요구사항을 기존 검사에 반영하고 PC·모바일 화면을 확인한다. `build:release`는 실제 승인 조건을 갖춘 공개 전환 단계에서만 사용한다.
